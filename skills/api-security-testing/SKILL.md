# API与主体核验卡

先列授权接口、角色、测试账号和可操作资源。对照正常身份与待验证身份，记录实际读取/修改了哪个主体的资源，检查服务端前置状态；通用成功响应和前端界面变化不能独立证明越权。

邮箱、Unicode/IDNA或大小写归一问题须沿注册、邀请、恢复、绑定及兑换追踪实际主体。仅使用受控账号与邮箱，确认消息去向、令牌关联和实际兑换结果；拼写碰撞或“已发送”提示本身不成立。

跨主机跳转、第三方认证或新资产先核范围，不能把新线索当新增授权。回显仅保存最小必要字段或凭据引用。未完成链路保留待跟进状态，不用Severity降级掩盖证据缺口。

## 从已知状态追到消费者

把已有证据整理成“来源编号/验证修订→已证实的输入或状态→材料证明存在的消费者→待核影响”。例如账号属性、绑定信息、对象状态或作业参数确实已保存后，再检查已知登录、恢复、授权、兑换、作业和导出入口如何消费它。消费者须有前端、接口描述、流量或事实出处；不猜测不存在的入口，不把保存成功、“已发送”或普通200直接升级为权限改变。

一个GET的404或一次匿名拒绝，只限制当前方法和身份。材料已经出现POST/JSON、另一受控身份或不同对象时，作为独立验证格检查实际消费链。每张小卡只做一条未知边，写依据、对象/身份、已有基线、单一假设、最小可观察影响及停止条件；前提齐全才派发。跨协议转换保留两端真实表示及同一对象的关联证据，缺其中一端时留作不确定。

## 逐输入验证账本

先用 `list_verifications` 读取当前任务已有格，再按端点、方法、输入位置、受控身份与对象、具体技术、表示法/真假变体分别组织。一个参数或身份的阴性不能关闭其他参数、其他身份、其他编码或整个漏洞类别；未登记的格仍是未知。

查询/筛选/选择器输入先取得已知匹配和已知不匹配的基线，固定身份、业务对象、相邻字段及分页条件，再比较不同表示法的真实响应。逐格核对返回对象与权限，不只看状态码、长度或错误字样。原始JSON重复键、数字边界和编码差异需保留实际传输形式；被客户端重写或合并的输入不能算已测。

实际工具回执、事实或附件保存后，用 `record_verification` 引用本任务的活动、带证据事实或附件编号。`negative` 需要有效前提、baseline/test/control证据，且只适用于当前格；`confirmed` 还需实际影响证据，并另用 `report_finding` 记录漏洞。无账号/登录态/对象用 `missing_prerequisite`，被防护阻断用 `blocked`，观察不完整或原因不明用 `inconclusive`；这些状态都不是安全结论。

补充或纠正同一格前先读取最新修订号，以 `expected_revision` 更新；改变已有证实或阴性结论须说明原因。旧修订证据保留，重复同一观察或只更新时间不算新进展。
